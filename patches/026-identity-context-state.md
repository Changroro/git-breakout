# 저장소 이력 조회를 누적 상태로 전환

[수정 패치](026-identity-context-state.patch)는 [025](025-classified-board-exposures.md) 다음에 별도 운영 번들(`deploy/oracle/`)에 적용하는 변경분이다. 웹 코드는 바뀌지 않는다.

## 문제

2026-11-16 06:10 UTC 이후 수집이 멈췄다. 수집기의 `api.repository_identity_context` 호출이 RPC 제한 30초를 넘겨 매번 실패했고, 11-08부터는 경계에서 실패와 성공을 오갔다. 운영 데이터(저장소 2,890개)에서 이 함수는 200초 넘게 걸렸다.

[023](023-identity-context-scalars.md)은 행당 읽는 크기를 줄였지만, 함수는 여전히 요청한 저장소의 전체 이력(약 83만 행, 스냅샷 테이블의 3분의 1)을 매번 다시 계산했다. 이력은 2시간마다 쌓이고 지우지 않으므로 비용이 계속 커졌다. 레거시 행을 고르는 단계는 6.3GB 테이블 전체를 읽었고, Postgres 공유 메모리가 기본값 128MB라 대부분이 디스크 읽기였다.

## 변경

`radar.repository_identity_state`가 저장소 ID별로 검증된 관측의 트렌딩 진입 횟수와 마지막 관측 시각·트렌딩 여부를 누적한다. 관측 기록이 추가될 때 트리거가 이어서 갱신하고, 이전 시각의 관측이 들어오거나 스냅샷 행이 수정되면 해당 저장소만 전체 이력으로 다시 계산한다. 이름 기준 누적 테이블 `repository_state`(013)와 같은 방식이다.

조회 함수는 저장소마다 첫 관측, 마지막 관측, 최근 20개, 성장 비교 시점만 인덱스로 읽고 진입 횟수는 누적 상태에서 가져온다. 비용이 이력 길이와 무관해진다.

- 레거시 행: 관측 기록은 유효한 GitHub ID가 있는 행에만, 삽입 시점에만 생긴다(019 이관과 `record_repository_identity`). 그래서 ID가 없는 행이 곧 관측 없는 행이고, 이 조건의 부분 인덱스로 레거시 후보만 읽는다. 운영 데이터에서 ID 있는 행 2,134,092건은 모두 관측이 있고, ID 없는 490,084건이 정확히 레거시 행이다. 019 이후 스냅샷 행을 수정하는 경로는 없다.
- 이어 붙이기: 레거시 행이 모두 첫 검증 관측보다 앞서면 두 요약을 이어 붙여 계산한다. 레거시 마지막 행과 검증 첫 행이 모두 트렌딩이면 진입 1회를 뺀다.
- 레거시 행이 검증 관측 사이에 끼는 저장소는 기존과 같은 전체 이력 계산을 쓴다. 운영 데이터에는 없다.
- 누적 상태가 관측 기록과 어긋나면 조용히 틀린 값을 주지 않고 `Repository identity state is out of date`로 실패한다.

스냅샷 테이블에 커버링 인덱스(271MB)와 레거시 부분 인덱스(51MB)를 추가하고, 인덱스만으로 읽을 수 있도록 insert 기준 autovacuum 비율을 0.01로 낮춘다. 함수 시그니처와 응답 형식은 같다.

## 결과

운영 DB에서 트랜잭션으로 적용해 비교했다. 2,890개 전체 응답이 기존 함수와 같았고, 시간은 203초에서 첫 실행 8.2초, 이후 5.2~5.5초가 됐다. 적용(인덱스 두 개 생성과 상태 채우기)은 약 3분 걸렸고, 그동안 스냅샷 쓰기는 막히지만 읽기는 된다.

## 적용과 검증

```bash
git apply --check patches/026-identity-context-state.patch
git apply --reverse --check patches/026-identity-context-state.patch
npm run test:integration -- 019 023 026 backup
npm test -- deploy/oracle/operations.test.ts
```

적용 전 백업 시각이 마지막 스냅샷 이후인지 확인하고, 수집 타이머를 멈춘 뒤 기존 배포 절차(`github-trend-radar-deploy.service`)로 적용한다. 적용 뒤 타이머를 다시 켜고 새 스냅샷 저장과 `/api/status`의 `ok`를 확인한다.

`regression-026.mjs`는 이름 변경, 이름 재사용, 레거시→검증 경계의 트렌딩, 레거시가 중간에 낀 경우, 같은 시각의 레거시·검증 행, 이전 시각 관측 삽입, 스냅샷 수정, 20개 넘는 이력, 성장 비교 시점에서 023 함수와 응답이 같은지 확인한다. 누적 상태가 처음부터 다시 계산한 값과 같은지, 마이그레이션을 다시 적용해도 같은지, 상태가 어긋나면 실패하는지도 확인한다.
