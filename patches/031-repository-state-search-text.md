# 이름별 상태의 payload 사본 제거와 WAL 압축

[수정 패치](031-repository-state-search-text.patch)는 [030](030-collection-cold-path.md) 다음에 별도 운영 번들(`deploy/oracle/`)에 적용하는 변경분이다. 웹 코드와 수집기 코드는 바뀌지 않는다.

## 문제

이름별 상태(`radar.repository_state`)는 저장소마다 마지막 스냅샷 행의 payload를 한 벌 더 갖고 있다(`payload_json`). 같은 payload가 `snapshot_repositories`에 이미 있다.

- 수집 완료(`api.complete_collection`)는 수집마다 저장소 2,900개분의 사본을 다시 쓴다. 체크포인트 뒤 처음 실행한 수집 완료의 WAL 77~88MB 가운데 29.0MB, 통째로 기록한 페이지 10,293개 가운데 3,679개가 이 테이블이다(030 문서의 측정).
- 보관함 검색(`api.archive_page`에 검색어를 준 호출)은 검색할 때마다 사본 5.9만 개를 모두 읽어 이름·설명·언어·토픽을 꺼낸다. 운영에서 4.7~5.2초 걸렸다.
- 테이블이 176MB다(힙 90MB, 나머지는 TOAST와 인덱스).

030 뒤에도 수집 한 번은 체크포인트 뒤 처음 고치는 페이지 약 1만 개를 통째로 WAL에 쓴다.

## 변경

### payload 사본 제거

`repository_state.payload_json`을 없애고 그 자리에 `search_text`를 둔다. 보관함 검색이 맞춰 보는 문자열(이름, 설명, 언어, 토픽을 이어 소문자로 바꾼 것)이고 `radar.repository_search_text`가 만든다. 식은 013의 `archive_page`가 검색할 때마다 계산하던 것과 같다. 마이그레이션은 열 타입을 바꾸면서 테이블을 한 번 다시 쓴다.

`api.archive_page`는 검색을 `search_text`로 하고, 응답에 싣는 payload는 상태 행이 가리키는 스냅샷 행(`latest_snapshot_id`, 이름)에서 읽는다. 한 쪽에 싣는 저장소(최대 100개)만 읽는다. 응답 형식은 같다.

이름별 상태 트리거(`update_repository_state`)는 payload 대신 `search_text`를 쓰고, push 시각과 트렌딩 여부는 023의 생성 열에서 가져온다. 나머지 열에 쓰는 값은 같다.

테이블은 `fillfactor` 50으로 두고 마지막 관측이 최근인 순서로 정렬해(`cluster`) 다시 쓴다. 수집마다 갱신되는 행이 이웃한 페이지에 모이고, 새 행 버전이 같은 페이지에 들어갈 자리가 생긴다.

달라지는 점은 두 가지다.

- 스냅샷 행을 나중에 고치면 보관함은 고친 값을 보여 준다. 지금까지는 사본이 고치기 전 값으로 남았다. 수집기 역할은 스냅샷 행을 고치거나 지울 권한이 없다(`select`, `insert`만 있다).
- payload의 `topics`가 배열이 아니면 지금까지는 보관함 검색이 실패했고, 이제는 그 수집이 실패한다. `topics`가 없는 payload는 전과 같이 토픽 없이 처리한다.

### WAL 압축

`docker-compose.yml`의 DB 명령에 `wal_compression=lz4`를 더했다. 운영 DB에서 세션 설정으로 재면 체크포인트 직후 수집 완료의 WAL이 약 90MB에서 59MB가 됐다(통째로 기록한 페이지 11,636개). 운영 이미지(`postgres:17.6-alpine`)는 lz4를 지원한다.

## 결과

운영 DB(030까지 적용된 상태)에서 확인했다(2026-11-17 UTC).

**사본과 원본이 같은지(읽기 전용, 04:43).** 이름별 상태 58,741행 전부에서 payload 사본이 그 행이 가리키는 스냅샷 행의 payload와 같았다. 이름·순위·시각도 같았고, 가리키는 행이 없는 경우는 없었다. 그래서 어느 쪽, 어느 검색어에서도 보관함 응답이 같다.

**트랜잭션으로 적용해 비교하고 롤백(04:48).**

| 비교 | 결과 |
|---|---|
| 보관함 조회 8가지(검색어 없이 1쪽·7쪽·범위 밖 쪽, 검색어 `python`·`rust agent`·`mcp server`·없는 말, 쪽 크기 10~100) | 응답 md5 모두 같음 |
| 수집 요약, 저장소 이력 조회 | 응답 md5 같음 |

수집 완료 비교에서 `radar.snapshots` 행만 달랐다. `created_at`의 기본값 `now()` 때문이다. 입력은 최신 스냅샷에 공식 트렌딩 진입 40건과 이름 표기 변경 10건을 넣은 2,919개다.

| 측정 | 이전 | 이후 |
|---|---|---|
| 보관함, 검색어 없는 호출 | 각 0.27~0.30초 | 여덟 호출 합쳐 1.07초 |
| 보관함, 검색어 있는 호출 | 각 4.7~5.2초 | 〃 |

| 이름별 상태 트리거 | 442~535ms, WAL 8.4MB(통째 기록 포함 29.0MB) | 287~296ms, 1.3MB |
| 수집 완료 WAL(체크포인트 사이 두 번째 실행, 통째 기록 없음) | 18.8MB | 11.6~12.1MB |

체크포인트 직후 수집 완료의 WAL은 새 함수로 재지 못했다. 트랜잭션 안에서 테이블을 다시 쓰면 그 페이지는 통째 기록 대상에서 빠지기 때문이다. 이름별 상태가 차지하던 29MB가 대부분 빠질 것으로 추정한다.

적용은 약 4초 걸렸다(테이블 다시 쓰기 3.4~3.5초, 정렬 0.6초). 그동안 스냅샷 쓰기가 막히고, 이름별 상태를 읽는 보관함 조회와 수집 요약이 기다린다.

## 적용과 검증

```bash
git apply --check patches/031-repository-state-search-text.patch
git apply --reverse --check patches/031-repository-state-search-text.patch
npm run test:integration -- core 017 027 028 030 031 backup
npm test -- deploy/oracle
```

수집 중이 아닐 때 기존 배포 절차(`github-trend-radar-deploy.service`)로 적용한다. 5초 넘게 쓰는 트랜잭션이나 5초 넘게 도는 보관함 조회가 있으면 `lock_timeout`으로 실패하고 다음 배포 주기에 다시 시도된다. 적용 뒤 보관함 화면과 검색이 열리는지, 다음 정기 수집이 성공하는지, `/api/status`가 `ok`인지 확인한다.

`wal_compression`은 배포 절차가 DB 컨테이너를 다시 만들지 않으므로 저절로 켜지지 않는다. 재시작 없이 켜려면 `alter system set wal_compression = 'lz4'; select pg_reload_conf();`를 실행한다. 컨테이너를 다시 만들 때는 compose의 설정이 적용된다.

030을 이미 적용한 DB에는 030 파일을 고쳐 다시 적용할 수 없어(체크섬 검사) 이 변경을 별도 번호로 나눴다.

`regression-031.mjs`는 013의 초기 채움 쿼리로 payload 사본을 가진 참조 테이블을 만들고 013의 `archive_page`를 그 테이블에 붙여 참조 구현으로 쓴다. 열흘치 스냅샷(트렌딩 드나듦, 이름 표기 변경, 설명·언어 없음, 토픽 없음, 토픽 키 없음, 최신 스냅샷에만 있는 저장소)에서 이름별 상태의 모든 열이 참조 테이블과 같은지, `search_text`가 사본으로 만든 값과 같은지, 쪽 번호·쪽 크기·검색어(이름, 언어, 토픽, 설명, 여러 낱말, 대소문자, 없는 말) 열한 가지 호출의 응답이 같은지 확인한다. 마이그레이션을 다시 적용해도 같은지, 테이블이 최근 관측순으로 저장되는지도 확인한다. 트리거가 쓰는 나머지 열은 `regression-core.mjs`, `regression-017.mjs`, `regression-027.mjs`, `regression-028.mjs`도 지난다.
