# 수집 한 사이클이 읽고 쓰는 페이지 줄이기

[수정 패치](030-collection-cold-path.patch)는 [029](029-classification-version-floor.md) 다음에 별도 운영 번들(`deploy/oracle/`)에 적용하는 변경분이다. 웹 코드와 수집기 코드는 바뀌지 않는다. 029와는 서로 기대지 않는다.

## 문제

DB를 재시작한 뒤 첫 정기 수집(2026-11-17 03:10 UTC)에서 저장소 이력 조회(`api.repository_identity_context`)가 13.7초, 수집 완료(`api.complete_collection`)가 6.1초 걸렸다. 캐시가 찬 상태에서는 각각 2.8~3.4초, 2.2~2.5초다. 수집기 RPC 제한은 30초다.

운영 DB에서 노드별로 쟀다(최신 스냅샷의 저장소 2,919개 요청, 캐시가 찬 상태). 이력 조회는 공유 버퍼를 428,115번 읽었다(본 쿼리 401,231 + 사전 검사 26,884).

- 저장소마다 최근 관측 20개를 인덱스 두 개로 하나씩 찾았다. 52,681번 탐침에 281,699번 읽었다.
- 요청마다 레거시 행(GitHub ID 없이 저장된 옛 기록) 157,144개를 다시 읽어 세 번 정렬했고, 세 번 모두 `work_mem` 4MB를 넘어 디스크를 썼다(약 1.9초). 레거시 행은 2026-09-12 이후로 생기지 않는다.
- 마지막에 저장소 요약과 성장 비교 시점을 묶는 조인이 중첩 루프로 돌아 502만 행을 버렸다(약 1.2초).
- 저장소마다 첫 검증 관측과 마지막 검증 관측을 따로 찾았다(61,642번). 첫 관측은 한번 정해지면 바뀌지 않는다.
- 최근 두 스냅샷은 아직 정리(vacuum)되지 않아 인덱스만으로 읽지 못하고 힙을 약 8,800번 따로 읽었다.

수집 완료는 체크포인트 뒤 처음 실행하면 WAL을 77~88MB 쓰고 페이지 10,293개를 통째로 기록한다. 그중 9.2MB와 1,306페이지는 값이 바뀌지 않는 발견 이력(`repository_discovery_milestones`) 행을 매번 다시 쓴 것이다.

수집 요약(`api.collection_summary`)은 최근에 관측한 저장소 9,315개마다 성장 비교 시점을 인덱스로 찾는데, 그 가운데 3,914개는 처음 관측한 지 `growth_days`가 안 돼 비교 시점이 있을 수 없다.

## 변경

### 저장소 이력 조회

`radar.repository_identity_state`(026)가 저장소마다 조회에 필요한 값을 모두 갖는다. 첫 검증 관측의 시각·별·트렌딩 여부, 마지막 관측의 순위·push 시각, 최근 관측 20개의 시각과 별(최신순 배열)을 추가했다. 관측이 뒤에 붙으면 트리거가 새 관측을 배열 앞에 붙이고 20개로 자른다. 026과 같은 조건(이전 시각의 관측, 스냅샷 행 수정)과 배열이 빈 행은 저장소 단위로 전체 이력에서 다시 계산한다.

`radar.repository_legacy_summary`가 이름별로 레거시 행의 첫 행(시각·별·트렌딩), 트렌딩 진입 횟수, 마지막 행(시각·별·트렌딩)을 저장한다. 운영 데이터에서 19,098행이다. 스냅샷 행을 insert·update·delete·truncate하는 문장마다 트리거가 해당 이름만 다시 계산한다. GitHub ID가 있는 행의 insert는 요약을 건드리지 않는다.

조회 함수는 저장소마다 누적 상태 한 행을 읽고, 관측 인덱스에서 마지막 관측 시각(상태가 최신인지 검사)과 성장 비교 시점만 찾는다. 첫 관측이 성장 비교 기준 시각보다 뒤인 저장소는 비교 시점을 찾지 않는다. 요청한 이름에 레거시 요약이 있으면 아래 조건을 모두 만족할 때 요약만으로 계산한다.

- 그 저장소에 허용된 이름 가운데 레거시 요약이 있는 이름이 하나다.
- 레거시 마지막 행이 첫 검증 관측보다 앞선다.
- 검증 관측이 20개 이상이다. 그래야 최근 20개가 모두 검증 관측이다.
- 레거시 마지막 행이 성장 비교 기준 시각 이전이다. 그래야 검증 관측에 비교 시점이 없을 때 레거시 마지막 행이 비교 시점이 된다.

하나라도 어긋나는 저장소는 026의 쿼리를 그대로 옮긴 `radar.repository_identity_row_context`로 계산한다. 레거시 행이 검증 관측 사이에 끼는 경우, 이름이 바뀌어 레거시 이름이 둘인 경우, 검증 관측 없이 레거시만 있는 경우가 여기에 든다. 운영 최신 요청에서는 2,919개 가운데 35개이고 약 3,800번 읽는다. 이름과 저장소의 연결(`repository_identity_aliases`)은 조회할 때마다 읽으므로 별칭이 바뀌면 바로 반영된다.

누적 상태가 관측 기록과 어긋나거나 새 열이 비어 있으면 026과 같이 `Repository identity state is out of date`로 실패한다. 이 검사는 본 쿼리 안으로 옮겨 상태 행을 한 번만 읽는다. 함수에는 `work_mem = 32MB`를 붙여 응답 정렬(약 6MB)이 디스크로 가지 않게 했다. 028의 `jit = off`는 유지한다.

누적 상태 테이블은 `fillfactor`를 50으로 두고, 전체를 다시 계산할 때 마지막 관측이 최근인 순서로 넣는다. 수집마다 갱신되는 저장소가 이웃한 페이지에 모이고, 새 행 버전이 같은 페이지에 들어가 인덱스를 다시 쓰지 않는다. 운영 최신 요청의 2,919행이 285페이지에 들어갔다.

`snapshot_repositories`의 insert 기준 autovacuum을 행 비율 0.01(약 2.6만 행, 스냅샷 9개 분량)에서 1,000행으로 바꾼다. 수집 한 번이 약 2,900행이므로 수집이 끝나면 곧 정리되어 다음 조회가 힙을 읽지 않는다.

### 수집 완료

발견 이력을 쓰는 문장이 바뀔 것이 없는 행을 건드리지 않는다. 지금까지는 수집한 저장소 전부를 `on conflict do update`로 다시 썼고, 조건을 `do update`에만 달면 행 잠금 기록이 남는다. 그래서 기존 행과 미리 조인해 새 저장소, 표기가 바뀐 이름, 처음 공식 트렌딩에 든 저장소만 넘긴다. 저장되는 값은 같다.

관측이 붙을 때 누적 상태를 갱신하는 트리거는 `insert … on conflict`를 `update`로 바꿨다. 갱신 대상은 항상 이미 있는 행이다. 함수에는 `work_mem = 64MB`를 붙여 수집 한 번의 payload(약 10MB)를 담는 트리거 전이 테이블이 임시 파일로 가지 않게 했다.

### 수집 요약

성장 비교 시점을 찾는 조건에 "첫 관측이 기준 시각 이전"을 더했다. 이름의 첫 관측보다 앞선 행은 없으므로 결과는 같다. 응답 정렬이 디스크로 가지 않게 `work_mem = 32MB`를 붙였다.

## 결과

운영 DB에서 트랜잭션으로 적용해 비교하고 롤백했다(2026-11-17 04:26 UTC, 캐시가 찬 상태).

| 이력 조회 요청 | 이전 | 이후 | 응답 |
|---|---|---|---|
| 최신 스냅샷의 저장소 2,919개 | 2.8~3.1초 | 0.61~0.67초 | md5 같음 |
| 150회 전 스냅샷의 저장소 2,955개 | 3.9~4.2초 | 0.63초 | md5 같음 |
| 레거시 이름이 있는 저장소 5,999개 표본 | 7.3~8.4초 | 2.0~2.2초 | md5 같음 |

최신 스냅샷 요청의 공유 버퍼 읽기는 428,115번에서 55,936번으로, 임시 파일 읽기는 8,686페이지에서 0으로 줄었다. 남은 읽기는 별칭과 레거시 요약 12,633번, 누적 상태 14,146번, 관측 인덱스의 마지막 관측 시각 11,677번, 성장 비교 시점 13,693번, 행으로 계산하는 35개 약 3,800번이다.

캐시가 빈 상태의 시간은 재지 못했다(캐시를 비우려면 재시작이 필요하다). 읽기 횟수는 캐시가 빈 상태에서 읽는 페이지 수의 상한이다. 실제로 읽는 서로 다른 페이지는 이전 약 1.3만~1.9만에서 이후 약 5천~6.5천으로 추정한다(저장소마다 관측 인덱스 리프 1~2장이 약 3천~4.6천, 별칭 약 1,100, 누적 상태 약 500, 레거시 요약 약 230, 성장 비교 시점의 스냅샷 인덱스 약 100~300). 03:10의 13.7초(계산 3.2초 + 읽기 10.5초)에 같은 비율을 적용하면 캐시가 빈 상태에서 약 4~5초로 추정한다.

수집 완료는 같은 입력(최신 스냅샷에 공식 트렌딩 진입 40건과 이름 표기 변경 10건을 넣은 2,919개)으로 이전 함수와 새 함수를 각각 실행해 저장 결과를 비교했다. 발견 이력, 이름별 상태, 누적 상태(026의 열), 별칭, 관측, 스냅샷 행, 스냅샷 요약, 실행 기록, 보드 노출, 적중률 요약의 md5가 모두 같았다. `radar.snapshots` 행만 달랐는데 `created_at`의 기본값 `now()` 때문이다. 수집 뒤의 이력 조회 응답도 같았고, 누적 상태와 레거시 요약은 전체를 다시 계산한 값과 같았다.

| 수집 완료 | 이전 | 이후 |
|---|---|---|
| 전체(캐시가 찬 상태) | 2.2~2.5초 | 1.9~2.1초 |
| 관측 기록 트리거(`record_repository_identity`) | 529ms | 322~370ms |
| 그 안의 누적 상태 갱신 | 220ms, WAL 레코드 11,606개 | 79~95ms, 2,935개 |
| 이름별 상태 트리거(`update_repository_state`) | 516ms | 442~469ms |
| 스냅샷 요약 트리거 | 270ms | 267~278ms |
| 발견 이력 쓰기(체크포인트 직후) | 117ms, WAL 9.2MB, 통째로 기록한 페이지 1,306개 | 33ms, 0.4MB, 63개 |
| 레거시 요약 트리거(새로 추가) | - | 3~5ms |

수집 요약은 응답의 md5가 같았고, 읽기는 76,081번에서 60,425번으로, 시간은 0.77초에서 0.70초로 줄었다.

적용은 약 17.5초 걸렸다(레거시 요약 1.3초, 누적 상태 다시 계산 16.2초). 그동안 스냅샷 쓰기는 막히고 읽기는 된다. 누적 상태 테이블은 3.7MB에서 약 28MB가 된다.

## 남은 비용

수집 완료가 캐시가 빈 상태에서 느린 것은 수집 한 번이 약 1만 페이지를 읽고 고치기 때문이다. 체크포인트 직후 실행의 WAL 77~88MB를 문장별로 나누면 다음과 같다.

| 문장 | WAL | 통째로 기록한 페이지 |
|---|---|---|
| 스냅샷 행 insert(인덱스 4개 포함) | 24.5MB | 2,822 |
| 이름별 상태(`repository_state`) 갱신과 사전 검사 | 29.0MB | 3,679 |
| 관측 insert | 13.7MB | 2,088 |
| 발견 이력(이번에 제거) | 9.2MB | 1,306 |
| 별칭 갱신 | 2.6MB | 373 |

이번 변경 뒤에도 남는 것은 모두 저장 결과 자체다. 이름마다, 저장소마다 인덱스 리프 한 장씩을 고치고 payload를 두 테이블에 쓴다. 줄이려면 저장하는 내용이나 서버 설정을 바꿔야 해서 이 패치에 넣지 않았다.

- `repository_state.payload_json`은 스냅샷 행에 이미 있는 payload의 사본이고 수집마다 저장소 2,900개분을 다시 쓴다. `api.archive_page`가 스냅샷 행을 읽게 하면 없앨 수 있다.
- `wal_compression = lz4`를 켜면 체크포인트 직후 수집 완료의 WAL이 약 90MB에서 59MB가 된다(운영에서 세션 설정으로 측정, 통째로 기록한 페이지 11,636개).
- payload 열의 압축을 lz4로 바꾸는 것은 쟀지만 넣지 않았다. 쓰기는 행 2,919개에 100~150ms 빨라지지만 저장 크기가 평균 1,855바이트에서 2,035바이트로 늘어 2KB를 넘는 행이 9%에서 57%가 되고, 그만큼 TOAST로 밀려나 읽기가 느려졌다(같은 조회 51ms → 88ms).
- 외래 키 검사 세 개가 행마다 돌아 합쳐 약 220ms다. 제약을 없애야 줄어든다.
- 수집 요약은 최근에 관측한 이름마다 이력 인덱스 리프 한 장을 읽는다(약 5,400개). 이벤트 신호 조회(`api.event_signal_context`)는 72시간치 이벤트 103MB를 순서대로 읽고 임시 파일 222MB를 쓰며 1.9초 걸린다. 둘 다 이력이 쌓여도 커지지 않는다.

## 적용과 검증

```bash
git apply --check patches/030-collection-cold-path.patch
git apply --reverse --check patches/030-collection-cold-path.patch
npm run test:integration -- 017 019 023 026 027 028 030 backup
npm test -- deploy/oracle/operations.test.ts
```

수집 중이 아닐 때 기존 배포 절차(`github-trend-radar-deploy.service`)로 적용한다. 첫 문장이 `snapshot_repositories`를 잠그므로 5초 넘게 쓰는 트랜잭션이 있으면 `lock_timeout`으로 실패하고 다음 배포 주기에 다시 시도된다. 적용 뒤 다음 정기 수집의 성공과 `/api/status`의 `ok`를 확인한다. `radar.repository_legacy_summary`가 19,098행인지, `radar.repository_identity_state`에 `recent_captured_at`이 빈 행이 없는지도 확인한다.

`regression-030.mjs`는 026의 함수를 참조 구현으로 만들어 응답을 비교한다. 요약으로 계산하는 경우(레거시 뒤에 검증 관측 20개 이상, 경계의 트렌딩, 검증 관측만 있는 저장소, 새 저장소, 다른 저장소가 쓰던 이름)와 행으로 계산하는 경우(검증 관측 19개, 레거시 이름 둘, 레거시만 있는 저장소, 레거시가 중간에 낀 저장소, 레거시가 성장 비교 구간 안에 있는 저장소)를 모두 넣고, 행 계산 함수를 실패하는 함수로 바꿔 각 저장소가 기대한 경로로 가는지 확인한다. 레거시 행을 뒤에 추가·수정·삭제했을 때, 이전 시각의 관측을 넣었을 때 누적 상태와 레거시 요약이 전체를 다시 계산한 값과 같은지, 마이그레이션을 다시 적용해도 같은지, 새 열이 비면 실패하고 다음 관측에서 다시 계산되는지도 확인한다. 수집 완료는 017의 함수를 참조 구현으로 만들어 새 저장소, 공식 트렌딩 첫 진입, 이름 표기 변경, 수집 공백 뒤의 발견 이력이 같은지와 바뀌지 않는 행을 다시 쓰지 않는지 확인한다. 수집 요약은 `regression-027.mjs`와 `regression-028.mjs`가 013의 원래 함수와 비교한다.

`regression-026.mjs`는 누적 상태 비교를 026이 만든 열 네 개로 한정했다. 이 테스트는 026을 다시 적용하는데, 026의 함수는 030이 추가한 열을 쓰지 않는다.
